# Isolated local-agent log probe

This is a separate, experimental Manifest V3 extension. It does **not** modify Clockoli's manifest, service worker, stores, time records, or agent logs. It has only the `alarms` permission and no host permissions, content scripts, or network calls. It never uploads source data. Do not package it as Clockoli.

The [Agent Activity Collector architecture and validation plan](ARCHITECTURE.md) uses these probe results. This probe remains separate from the Phase 1 collector now implemented in Clockoli; its permission and restart observations are not evidence that the installed collector passed its live gate.

## Manual test on this Mac

From the repository root, run `node experiments/local-agent-logs/live-check.mjs` to start an **isolated Google Chrome profile**. Chrome 158 ignores command-line extension loading, so the runner enables Developer mode and opens **Load unpacked**; select the absolute `experiments/local-agent-logs/` directory in the native picker. The runner then opens `probe.html`. In that page select `~/.codex/sessions` and `~/.claude/projects` with the two buttons. Do not choose their parent directories. No agent file is modified.

The runner checks a scan with the page open, closes only its probe page, waits for a real alarm-driven scan with no extension page, completely closes that **isolated Chrome instance**, launches the same profile again, and waits for a startup/alarm scan without an extension page. It prints only permission states, read byte/line/file counts, error codes, and run numbers. The isolated browser profile (including its handles) is deleted on completion. It does not close or restart your normal Chrome installation.

`node experiments/local-agent-logs/live-check.mjs --chromium` uses the already-installed Playwright Chromium and loads the prototype automatically; directory selection still requires a user gesture. This is a Chromium fixture, **not** evidence for Google Chrome's restart-time permission policy.

For the persistent-grant experiment, use `node experiments/local-agent-logs/live-check.mjs --persistent` in a fresh isolated **Google Chrome** profile. First choose both directories in the probe page. The runner closes that page, records the alarm result with no extension page, then reopens it and loads the same handles **from IndexedDB**. If permission is `prompt`, it clicks each provider's **Allow read access** control, which calls `requestPermission({mode:'read'})` in response to a page gesture. If Chrome presents **Allow on every visit**, choose that option for each provider; note whether the option actually appears. The runner then closes the page again, checks another real alarm, fully restarts that isolated Chrome, and checks background read permission and file counts before any extension page opens. It cannot itself choose a browser permission response. A granted response while a page is open does not prove persistence; only the later no-page and restart checks do.

Run the deterministic synthetic test with `npx playwright test test/agent-log-probe.browser.spec.js --workers=1` and the parser test with `node --test test/agent-log-probe.test.js`. The synthetic test uses only self-created, isolated OPFS fixture records. OPFS handles prove IndexedDB serialization, service-worker access, alarm processing, and catch-up after a browser restart; they do **not** substitute for native local-directory permission testing.

## Experiment boundaries

- The picker requests read access only in the visible extension page. FileSystemDirectoryHandles and per-file cursors are saved in this extension's own IndexedDB. Cursor keys hash relative paths; saved metadata contains byte offset, beginning-of-file fingerprint, file modification time, and fixed-category event counts, never source JSONL lines or incomplete text.
- A one-minute `chrome.alarms` tick and browser startup attempt a bounded read from the service worker. It never calls `requestPermission` there. A restored handle with `prompt` or `denied` permission blocks automatic processing until a user reauthorizes in the visible page.
- Each scan limits enumeration to 20,000 entries / 5,000 JSONL files and reading to 64 MiB, 128 advanced files, and 16 MiB per file. An incomplete trailing JSONL line remains at its previous offset and is reread on a later scan. A truncated or replaced file rewinds its own cursor and counts. Malformed records fail that file without advancing its cursor. If an incomplete line exceeds the chunk limit, it remains blocked with a safe error code.
- Alarms are best-effort and do not run while Chrome is closed or the computer is asleep. On reopening, the worker rescans the selected trees and resumes from stored offsets. `FileSystemObserver` is deliberately not used in the worker: its support and lifetime are separate from the alarm-backed path.
- This prototype measures read/access and incrementality, not exact agent-active time, human approval waits, task attribution, or writing Clockoli time records. The current implementation has no policy for stale cursors of deleted files, concurrent scans across worker crashes, or quota/storage eviction. It is not a production feature.

## Observed boundary (Chrome for Testing / Chromium 151)

On the actual local Codex and Claude Code directories, selection and a page-initiated worker scan succeeded with `granted` permission and read thousands of JSONL lines. **After the probe page closed**, the next real alarm fired with no extension page but `queryPermission({mode:'read'})` returned `prompt` for both stored directory handles; it read zero files. After completely closing and reopening that isolated browser profile, the next alarm again saw `prompt` and read zero files. IndexedDB had retained both handles: the worker could query them, but could not silently obtain permission. This directly rules out unattended native-directory background scanning in that tested browser/profile configuration. It does not establish what branded Google Chrome 158 does with a manually installed extension.

The first live run used a 1 MiB per-file read budget and encountered `line_too_large` on real logs. A subsequent local, content-free size scan found real JSONL lines up to about 11.7 MiB; the read budget was raised to 16 MiB per file and a synthetic 12 MiB line passes the browser test. The later installed-Chrome experiment below did scan real native directories with this budget, but its per-alarm 64 MiB cap left a Codex backlog; do not treat one run's counters as complete event coverage.

## Installed Google Chrome 158 / actual Clockoli origin

A temporary read-only probe in the already installed Clockoli extension (not its checked-in source) saved both previously selected directory handles into a **separate experimental IndexedDB database**. The actual installed Clockoli service worker restored both handles and read one bounded JSONL record per agent while an Activity page was open. After all Clockoli extension pages were closed, the same worker restored both handles but `queryPermission({mode:'read'})` returned `prompt` for **both**, so automatic reading was not possible. No browser restart was necessary to reach this blocking state. The temporary database was then deleted and its absence verified. The production Clockoli database, worker source, permissions, and agent logs were not modified.

This is an empirical result for the current installed Chrome 158/Clockoli origin: retaining the handles in IndexedDB alone does not provide unattended background access when no extension page remains open. It does not prove how Chrome behaves after a full restart under a future persistent-grant configuration.

## Restored-handle `requestPermission` retest in existing Chrome 158.0.8127.37

The user selected the real `sessions` and `projects` directories in the **separate** `Clockoli Local Log Read-only Probe` extension, installed into their existing Chrome profile (not the Clockoli origin). Both handles were written to and read back from that probe's IndexedDB. Initial worker scans while the page was open returned `granted` and read bounded JSONL metadata. After closing its only page, direct service-worker checks returned `prompt` for both handles; worker enumeration raised `NotAllowedError`.

The probe page was reopened and retrieved the *stored* handles, with `queryPermission({mode:'read'}) === 'prompt'` for both. A trusted click on the probe's **Разрешить чтение снова** control called `requestPermission({mode:'read'})` on the restored Codex handle. Chrome returned `granted` promptly; both stored handles then queried `granted` on the page. The user later clarified that Chrome **did offer `Allow on every visit` and they selected Yes**; this browser-level choice was reported by the user, not captured in the probe's page DOM, and its exact prompt timing was not recorded. After closing the only extension page again, the service worker **still** queried `granted` and enumerated both directories. Five minutes later, with no probe or extensions-manager page, alarm run 13 queried `granted` for both, visited 278 Codex files and 34 Claude files, and read 64 MiB of new Codex data with zero errors (Codex backlog remained; Claude had no new data at that point). A separate bounded 4096-byte read of one real JSONL file per provider succeeded directly in the worker without any extension page. Reloading **only the experimental extension**, without opening its page, created a new service worker; both stored handles still queried `granted`, enumerated, and had an alarm present. Thus the earlier `queryPermission`-only negative result was not a sufficient test of restored-handle authorization. This establishes unattended background reading after an explicit `requestPermission` in this current Chrome session, **not** permission persistence through a complete restart of the user's Chrome profile. The user has not authorized interrupting their other tabs for that test. At the end of this session, the alarm was cleared, the separate experimental IndexedDB was deleted and verified absent, and the test extension was uninstalled and verified absent from `chrome://extensions`; Clockoli remained installed.

## Full Google Chrome restart with real directories (2026-11-24)

The same unpacked source was reinstalled into the user's existing Google Chrome **158.0.8127.37** profile. The previous experiment had intentionally deleted the probe's IndexedDB, so the user **reselected** `~/.codex/sessions` and `~/.claude/projects`; their handles and cursors were saved to the probe's own IndexedDB. Chrome offered no new persistent-permission choice on this selection. With the page closed, the worker independently restored both handles, queried `granted`, and enumerated the directories. Before Quit, alarm run 6 read 64 MiB from Codex and about 9.9 MiB from Claude with zero errors.

The main Google Chrome process and its helpers were stopped with normal **Quit** and verified absent, then a new Chrome process started with the same profile. No probe page was opened. **First restart:** the saved handles were present, but native-handle `queryPermission()` and enumeration did not settle within bounded 10–12-second checks; the durable scan status remained at run 6 for several minutes despite an alarm being scheduled. Opening a probe page for diagnosis also initially stalled on the saved handle; no `prompt` result or new `Allow on every visit` choice was observed. Subsequently the page returned `granted` for both without another recorded permission choice. After closing the page and reloading *only the experimental extension*, alarm run 7 read 64 MiB of Codex data with `granted` for both handles and zero errors. This first restart was **not** a successful unattended scan and its exact stall cause was not established.

**Second restart:** Chrome and helper processes were again verified stopped, then Chrome was launched with no probe page. After several real alarm ticks, run 15 at `2026-11-24T19:04:52Z` returned `granted` for both restored handles, visited 275 Codex JSONL files and 34 Claude JSONL files, read 64 MiB of Codex data, and recorded zero errors. Directly in the worker, still with no probe page, `queryPermission()` returned `granted` and a bounded 4096-byte sample of one real JSONL file per provider was readable. Later run 22, after a synthetic-fixture interval described below, again used the **restored real handles**, queried `granted`, visited 416 Codex and 34 Claude files, read 64 MiB of Codex data, and recorded zero errors. **Correction confirmed by the user:** after this second Chrome restart a native window asked to choose/allow the directories again, and the user **did reselect/approve both directories before the successful alarm**. The agent checked for extension *tabs* but did not observe or account for that browser-level window. These `granted` scans therefore establish background work **after renewed user interaction**, not unattended access after a restart. Across the two complete restarts in this experiment, unattended native-directory tracking was **not demonstrated**; the first run stalled and the second required reauthorization. The earlier claim of a successful unattended restart was wrong.

No real agent-log file was created or changed by the probe. Metadata snapshots before and after the two restarts were identical: Codex 501 JSONL files / 1,422,471,439 bytes; Claude 34 JSONL files / 46,779,105 bytes, with unchanged maximum modification timestamps. Consequently, the experiment cannot claim to have observed a *new native log file* or a *new append to a real log*. Separately, while the browser was running after the second restart and **without opening any probe page**, a temporary OPFS directory inside the experimental extension was substituted for the Codex handle. Alarm run 18 processed one synthetic file and line; then one line was appended to that synthetic file and a second synthetic JSONL file was created. Durable cursor readback showed two lines in the original file and one in the new file; run 20 visited both with no further new lines or errors. The original real Codex handle was restored atomically, the temporary backup and synthetic OPFS directory were removed, and run 22 verified real-directory reading again. This proves the same worker's incremental catch-up logic against safe fixtures, **not** a newly written native Codex/Claude log.

### Third full restart with explicit no-interaction control (2026-11-24)

The user requested another test, this time explicitly agreeing **not to touch any native picker/permission window after restart** and to report whether one appeared. The existing saved handles already returned `granted` in the probe page and worker, so the user **did not select the directories again before this restart**. After the page was closed, real alarm run 33 at `2026-11-24T19:55:00Z` returned `granted`, visited 501 Codex and 34 Claude JSONL files without errors, and the worker independently read a bounded 4096-byte slice from one real JSONL file per provider. No probe page remained open.

Chrome **158.0.8127.37** was quit normally; the main and helper processes were both verified absent at `2026-11-24T20:57:03+01:00`. The same Chrome profile restarted with a new main PID at `20:57:17+01:00`, without opening a probe page. The user reported both shortly after startup and again after the subsequent checks that **no native selection/permission window appeared and they did not choose or approve any folders**. In the restored service worker, real alarm run 39 at `2026-11-24T20:02:00Z` independently queried `granted` for both IndexedDB handles, visited 501 Codex and 34 Claude JSONL files, and returned zero errors. A separate direct worker check at `20:02:28Z`, still with no probe page, queried `granted` and read a bounded 4096-byte slice of one real JSONL file per provider. This time the successful alarm occurred **without post-restart user interaction**. The result demonstrates that unattended background access after a full Chrome restart **is possible with the already-granted persisted handles in this profile**. The earlier stalled first restart remains a reliability caveat; it does not invalidate the successful controlled run or establish a cause for the earlier stall. Neither a native append nor a new native file was observed: the real directory counts, byte totals, and latest modification times stayed unchanged.

For safe post-restart incremental verification without changing agent logs, the worker temporarily scanned one synthetic JSONL in its own OPFS directory: run 43 processed one file and line. One synthetic line was appended and a second synthetic file created; alarm run 44 at `20:06:14Z` visited two files, advanced both cursors, and counted two new lines with zero errors. Cursor readback gave two complete lines in the original and one in the new file. The real Codex handle was then restored atomically, the temporary backup, both synthetic cursors, and the OPFS fixture were removed. Run 45 at `20:07:01Z` again queried `granted` and visited 501 real Codex and 34 real Claude files without errors. No production Clockoli file or agent JSONL was modified.

To reproduce: install this unpacked extension from this exact directory; in its page choose the two real directory roots, confirm any `Allow on every visit` prompt, close **all pages of this extension**, and record the worker's IndexedDB handle presence/permission and actual alarm run. Quit **the same Chrome profile completely** (verify main/helper process exit), reopen it without a probe page, **ask the user not to interact with any native browser permission/picker window until after the test**, wait for `chrome.alarms` to run, then read only the worker's safe `status.latest` and bounded permission/file-read outcomes. Confirm with the user whether any native window appeared or any approval occurred before declaring the run unattended. Do not confuse a worker reload, a DevTools reconnect, or a page visit with a full browser restart. Any repeated selection/approval makes that particular run attended.

After the third restart experiment, the separate probe extension and its IndexedDB (including both restored real handles) were **left installed** for inspection. Its one-minute alarm was cleared and verified absent to stop further scans in the current browser session. The probe's `onStartup` and module-initialization handlers recreate that alarm when the extension next starts (for example, on another browser or extension restart); clearing it once is not a permanent opt-out. The user may choose to uninstall the probe after reviewing the result.
